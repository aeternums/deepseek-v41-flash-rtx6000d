# DeepSeek实测：16流2226 tok/s

用四张 RTX 6000D 跑 DeepSeek-V4.1-Flash，我最终把生产配置定在 **1M 上下文、16 个调度槽位**。平时有短文本对话和代码生成，也有一轮轮累积到几十万 token 的会话。对我来说，选型要回答两个问题：并发起来后吞吐能到多少，以及长请求进来后，短请求还要等多久。

## 怎么搭的

推理框架用 **vLLM**，在 Local Inference Lab 的镜像底座上应用 Fraser Price 的 **BRRR** 补丁。模型用 DeepSeek 官方原版 checkpoint，四卡做 **TP4**，由 **B12X** 提供注意力、MoE、线性层和 PCIe 卡间通信后端，常用执行形状由 CUDA Graph 捕获。

解码用 **DSpark**，每步最多提出 7 个草稿 token，按置信度自适应决定验证多少。长输入拆成 chunk 做预填充，单请求每块最多 2,048 token，调度批次预算 4,096 token。KV cache 用 FP8，Engram 小块读走 Linux 页缓存。这样既保留长上下文，也能让短请求和长请求共用一套服务，实际能否兼顾由下面的混合负载来检验。

## 实测怎么样

| 负载 | 单流 | 8 流合计 | 16 流合计 |
|---|---:|---:|---:|
| 短代码解码，约 2.15K 输入 | **548 tok/s** | **1,627 tok/s** | **2,226 tok/s** |
| 普通短对话，端到端 | **246 tok/s** | **842 tok/s** | — |

上面是同一生产配置的独立基准。代码单流取中位数，多流取共同解码窗口的合计吞吐。普通短对话从发出请求开始计时，8 流首 token p95 约 **353 ms**。

我还发了一条 **103.5 万 token** 的冷输入，模型成功找回指定标记并生成 4,096 token。长请求首 token 约 **190 秒**。它一开始生成，我就插入 8 个短请求，全部在长请求结束前完成，短请求首 token p95 **506 ms**。逐轮累积的热会话也单独测了，10 万 token 独立前缀的 8 流合计约 **750 tok/s**。冷长输入仍要等预填充，这次混合测试测的是长请求开始生成后的表现。
